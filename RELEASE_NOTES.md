# BlindPilot 0.29.5

Hermes on another computer now says why it refused the connection, instead of always blaming your password.

- Every refused WebSocket upgrade used to be reported the same way: "Hermes at ... refused the connection key. Check the key in Remote Hermes settings, then try again." Hermes refuses for reasons of its own far more often than it refuses a bad password, so that message sent people back to re-type a password the server had just accepted. If you knew the password was right, you were right, and BlindPilot was telling you otherwise.
- The status Hermes refused with is now read, and it, together with which credential was presented, decides what you are told. A sign-in that already succeeded is never reported as a wrong key; a missing gateway or a failing proxy is named as the address or the proxy; a refusal by something in between says so and points at the WebSocket.
- Hermes does not say which credential arrangement it is running, and the two want different things. A Hermes bound to a public address requires a login and refuses a session token outright; one bound to localhost has no login to offer and refuses a ticket. BlindPilot now asks which one it is talking to, so a token refused by a server that wants a login is answered with "choose Username and password", and a password refused by a server that wants a token with "choose Session token".
- A 400 from the login is reported as the address fault it is, not as a credential problem. Hermes answers 400 to a Host it was not told about, which is what a reverse proxy sending its own Host produces; the message now names `dashboard.public_url`, the setting that fixes it.
- Verified against a real `hermes serve` bound to a public address and to localhost, reached over plain `ws` and over TLS through a reverse proxy: every working arrangement still connects, and each refusal now names its own cause. The README's remote-Hermes section says which credential each arrangement wants and when `dashboard.public_url` is needed.
